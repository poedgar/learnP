````markdown
## Choosing a value with CASE

`CASE` picks a value depending on conditions, like an "if" for a single column. Each book
gets a length label:

```sql
SELECT title, pages,
       CASE
           WHEN pages < 300 THEN 'short'
           WHEN pages < 450 THEN 'medium'
           ELSE 'long'
       END AS length
FROM books;
```

The conditions are tried **in order**, and the first one that's true wins: a 250-page book
is "short" even though it's also under 450. `ELSE` covers everything else. Leave out `ELSE`,
and rows that match no condition get `NULL`.

## Counting with CASE

Put a `CASE` inside an aggregate to count or add up only some rows, several different ways
in one query. In-stock and out-of-stock books per genre, side by side:

```sql
SELECT genre,
       SUM(CASE WHEN in_stock = 1 THEN 1 ELSE 0 END) AS in_stock,
       SUM(CASE WHEN in_stock = 0 THEN 1 ELSE 0 END) AS out_of_stock
FROM books
GROUP BY genre;
```

Each `CASE` turns a row into 1 or 0, and `SUM` adds those up.

## Working with text

SQLite has functions for changing and taking apart text:

| Function | Gives |
|----------|-------|
| `UPPER(t)`, `LOWER(t)` | the text in capitals or small letters |
| `LENGTH(t)` | the number of characters |
| `SUBSTR(t, start, length)` | part of the text; the first character is position 1 |
| `REPLACE(t, find, with)` | the text with every `find` replaced |
| `TRIM(t)` | the text without spaces at either end |
| `INSTR(t, find)` | the position where `find` first appears, or 0 |

`||` joins pieces of text together:

```sql
SELECT UPPER(title) AS shouting,
       REPLACE(title, 'The ', '') AS without_the,
       title || ' by ' || author AS full_title
FROM books;
```

Functions can be nested. A customer's first name is everything before the first space:

```sql
SELECT name, SUBSTR(name, 1, INSTR(name, ' ') - 1) AS first_name
FROM customers;
```

## Working with numbers

You've met `ROUND`. `ABS` drops a minus sign. And watch out for **integer division**: when
both numbers are whole, SQLite divides and throws away the remainder.

```sql
SELECT 7 / 2, 7 / 2.0, 7 % 2, ABS(-3), ROUND(2 / 3.0, 2);
```

`7 / 2` is 3, but `7 / 2.0` is 3.5. `%` gives the remainder. If you need decimals from two
whole-number columns, multiply one of them by `1.0` first.

## Dates

The bookshop stores dates as text in the form `YYYY-MM-DD`. SQLite's date functions read and
write that form:

```sql
SELECT date('2026-03-14', '+7 days') AS a_week_later,
       date('2026-03-31', '+1 day') AS next_day,
       date('2026-03-14', 'start of month') AS month_start,
       strftime('%Y', '2026-03-14') AS year,
       strftime('%m', '2026-03-14') AS month;
```

`strftime` formats a date: `%Y` is the year, `%m` the month and `%d` the day. It makes
grouping by month easy. In which year did each customer join?

```sql
SELECT name, strftime('%Y', joined_on) AS joined
FROM customers;
```

## Days between dates

`julianday` turns a date into a day number, so subtracting two of them gives the days in
between. How many days before 8 April 2026 did each customer join?

```sql
SELECT name, joined_on, julianday('2026-04-08') - julianday(joined_on) AS days
FROM customers;
```

The result is a decimal number such as `157.0`. `NULL` in either date gives `NULL`.

## Converting with CAST, and NULLIF

`CAST(value AS type)` converts a value. Turning a decimal into an `INTEGER` drops the
fraction:

```sql
SELECT CAST('12' AS INTEGER) + 1, CAST(9.99 AS INTEGER), CAST(price AS TEXT)
FROM books
LIMIT 1;
```

`NULLIF(a, b)` gives `NULL` when `a` equals `b`, and `a` otherwise. Its classic use is
avoiding division by zero. In most databases dividing by 0 is an error; SQLite returns `NULL`,
but `NULLIF` makes your intention clear either way. The average price of each genre's
out-of-stock books, where some genres have none:

```sql
SELECT genre,
       ROUND(SUM(CASE WHEN in_stock = 0 THEN price ELSE 0 END)
             / NULLIF(SUM(CASE WHEN in_stock = 0 THEN 1 ELSE 0 END), 0), 2) AS average_out_of_stock
FROM books
GROUP BY genre;
```

## Putting it together

A month-by-month summary of orders and how many have shipped:

```sql
SELECT strftime('%Y-%m', ordered_on) AS month,
       COUNT(*) AS orders,
       SUM(CASE WHEN shipped_on IS NULL THEN 1 ELSE 0 END) AS waiting
FROM orders
GROUP BY month
ORDER BY month;
```
````

````markdown
## Why name the steps?

Subqueries in `FROM` let you build an answer in stages, but they read inside-out: the first
step is buried in the middle. `WITH` lets you write the steps **in order, with names**:

```sql
WITH sales AS (
    SELECT book_id, SUM(quantity) AS copies
    FROM order_items
    GROUP BY book_id
)
SELECT b.title, s.copies
FROM sales AS s
JOIN books AS b ON b.id = s.book_id
ORDER BY s.copies DESC, b.title;
```

`sales` is a **common table expression** (CTE): a named query that the rest of the statement
can use like a table. It exists only while this statement runs; nothing is saved.

## Several steps

Separate steps with commas. Each step can use the ones before it. Each order's total, then
the average order:

```sql
WITH order_totals AS (
    SELECT order_id, SUM(quantity * unit_price) AS total
    FROM order_items
    GROUP BY order_id
),
summary AS (
    SELECT COUNT(*) AS orders, ROUND(AVG(total), 2) AS average_order, ROUND(MAX(total), 2) AS biggest_order
    FROM order_totals
)
SELECT * FROM summary;
```

## Using a step twice

A named step can be used as often as you like. Books that sold more copies than the average
book: `sales` gives each book's copies, and also the average of them.

```sql
WITH sales AS (
    SELECT book_id, SUM(quantity) AS copies
    FROM order_items
    GROUP BY book_id
)
SELECT b.title, s.copies
FROM sales AS s
JOIN books AS b ON b.id = s.book_id
WHERE s.copies > (SELECT AVG(copies) FROM sales)
ORDER BY s.copies DESC, b.title;
```

Without `WITH`, you'd write the same subquery twice, as in lesson 5's *Above-average
spenders*.

## Recursion: a step that uses itself

`WITH RECURSIVE` lets a step refer to **itself**, so it can build rows one at a time. Counting
from 1 to 10:

```sql
WITH RECURSIVE counter(n) AS (
    SELECT 1
    UNION ALL
    SELECT n + 1 FROM counter WHERE n < 10
)
SELECT n FROM counter;
```

It has two parts joined by `UNION ALL`:

1. The **starting row**: `SELECT 1`.
2. The **recursive part**: `SELECT n + 1 FROM counter WHERE n < 10`. It runs on the rows made
   last time, over and over, until it produces no new rows.

The `WHERE n < 10` is what stops it.

## A calendar

Counting works for dates too. Every day in March 2026:

```sql
WITH RECURSIVE days(day) AS (
    SELECT '2026-03-01'
    UNION ALL
    SELECT date(day, '+1 day') FROM days WHERE day < '2026-03-31'
)
SELECT day FROM days;
```

## Finding the gaps

A calendar is useful because it has **every** day, including the ones missing from your
data. Join orders onto it with a `LEFT JOIN`, and keep the days with no match: the days in
March with no orders.

```sql
WITH RECURSIVE days(day) AS (
    SELECT '2026-03-01'
    UNION ALL
    SELECT date(day, '+1 day') FROM days WHERE day < '2026-03-31'
)
SELECT d.day
FROM days AS d
LEFT JOIN orders AS o ON o.ordered_on = d.day
WHERE o.id IS NULL;
```

That's 26 of March's 31 days. The `orders` table alone could never tell you this, because
the days with no orders aren't in it.

## Stopping

A recursive step without a stopping condition never ends. The sandbox stops any query after
3 seconds:

```sql
-- Error: nothing stops this counter, so the sandbox stops it after 3 seconds.
WITH RECURSIVE counter(n) AS (
    SELECT 1
    UNION ALL
    SELECT n + 1 FROM counter
)
SELECT COUNT(*) FROM counter;
```

Always check that the recursive part's `WHERE` eventually becomes false.

## Putting it together

Steps make long reports readable. Revenue per genre, with each genre's share of the total:

```sql
WITH genre_revenue AS (
    SELECT b.genre, SUM(oi.quantity * oi.unit_price) AS revenue
    FROM order_items AS oi
    JOIN books AS b ON b.id = oi.book_id
    GROUP BY b.genre
),
shop AS (
    SELECT SUM(revenue) AS total FROM genre_revenue
)
SELECT g.genre, ROUND(g.revenue, 2) AS revenue, ROUND(100.0 * g.revenue / shop.total, 1) AS percent
FROM genre_revenue AS g
CROSS JOIN shop
ORDER BY g.revenue DESC;
```

`CROSS JOIN` pairs every row on the left with every row on the right. `shop` has one row, so
it simply adds the total to each genre.
````

````markdown
## A window keeps every row

`GROUP BY` squashes each group into one row. Sometimes you want the group's figure **next to
every row** instead: each book with its genre's average price. A **window function** does
that. Add `OVER (…)` after an aggregate:

```sql
SELECT title, genre, price,
       ROUND(AVG(price) OVER (PARTITION BY genre), 2) AS genre_average
FROM books
ORDER BY genre, price;
```

All 16 books stay in the result. `AVG(price) OVER (PARTITION BY genre)` means "the average
price of the rows in this row's genre".

## PARTITION BY

`PARTITION BY` splits the rows into groups for the window, like `GROUP BY` does, but without
merging them. Leave it out and the window is the whole result:

```sql
SELECT title, price,
       ROUND(AVG(price) OVER (), 2) AS shop_average,
       COUNT(*) OVER (PARTITION BY genre) AS books_in_genre
FROM books;
```

## Numbering rows: ROW_NUMBER, RANK and DENSE_RANK

These functions number rows in the order given inside `OVER`. They only differ when there are
ties:

```sql
WITH scores(points) AS (VALUES (10), (10), (8))
SELECT points,
       ROW_NUMBER() OVER (ORDER BY points DESC) AS row_number,
       RANK() OVER (ORDER BY points DESC) AS rank,
       DENSE_RANK() OVER (ORDER BY points DESC) AS dense_rank
FROM scores;
```

- `ROW_NUMBER` always counts 1, 2, 3, breaking ties in no particular order.
- `RANK` gives ties the same number and then skips: 1, 1, 3.
- `DENSE_RANK` gives ties the same number without skipping: 1, 1, 2.

(`VALUES` makes a small table on the spot, which is handy for trying things out.)

With `PARTITION BY`, the numbering restarts for each group. Each customer's orders, newest
first:

```sql
SELECT customer_id, id, ordered_on,
       ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY ordered_on DESC) AS newest_first
FROM orders;
```

## Top N per group

You can't filter on a window function in `WHERE`, because windows are worked out after
`WHERE` runs:

```sql
-- Error: window functions can't be used in WHERE.
SELECT title
FROM books
WHERE ROW_NUMBER() OVER (ORDER BY price) <= 3;
```

Number the rows in a `WITH` step first, then filter. Each customer's most recent order:

```sql
WITH numbered AS (
    SELECT customer_id, id, ordered_on,
           ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY ordered_on DESC) AS n
    FROM orders
)
SELECT customer_id, id, ordered_on
FROM numbered
WHERE n = 1;
```

## Running totals

Put `ORDER BY` inside `OVER` and an aggregate becomes **running**: it covers the rows up to
the current one. How the customer list grew:

```sql
SELECT name, joined_on,
       COUNT(*) OVER (ORDER BY joined_on) AS customers_so_far
FROM customers;
```

Watch out for rows that share the sort value. They count as one step, so the running figure
jumps for all of them together. Two orders were placed on 7 March and three on 14 March:

```sql
SELECT id, ordered_on,
       COUNT(*) OVER (ORDER BY ordered_on) AS orders_so_far
FROM orders
WHERE ordered_on BETWEEN '2026-03-07' AND '2026-03-14';
```

Both 7 March orders show 2, and all three 14 March orders show 5. Add a tie-breaker, such as
`ORDER BY ordered_on, id`, to make it go up one row at a time.

## Looking at neighbours: LAG and LEAD

`LAG(column)` gives the value from the **previous** row in the window's order; `LEAD(column)`
gives the **next** one. The first row has no previous row, so `LAG` gives it `NULL`. Each
order's total next to the previous order's:

```sql
WITH totals AS (
    SELECT order_id, ROUND(SUM(quantity * unit_price), 2) AS total
    FROM order_items
    GROUP BY order_id
)
SELECT order_id, total,
       LAG(total) OVER (ORDER BY order_id) AS previous_total,
       LEAD(total) OVER (ORDER BY order_id) AS next_total
FROM totals;
```

## Window frames

A **frame** chooses exactly which rows around the current one the function sees.
`ROWS BETWEEN 2 PRECEDING AND CURRENT ROW` means "this row and the two before it": a moving
average of the last three orders.

```sql
WITH totals AS (
    SELECT order_id, SUM(quantity * unit_price) AS total
    FROM order_items
    GROUP BY order_id
)
SELECT order_id, ROUND(total, 2) AS total,
       ROUND(AVG(total) OVER (ORDER BY order_id ROWS BETWEEN 2 PRECEDING AND CURRENT ROW), 2) AS moving_average
FROM totals;
```

The first two rows have fewer than two rows before them, so their averages use what there is.

## Putting it together

Windows can run over grouped results, too. Each genre's revenue, its rank, and its share of
the total:

```sql
SELECT b.genre,
       ROUND(SUM(oi.quantity * oi.unit_price), 2) AS revenue,
       RANK() OVER (ORDER BY SUM(oi.quantity * oi.unit_price) DESC) AS position,
       ROUND(100.0 * SUM(oi.quantity * oi.unit_price) / SUM(SUM(oi.quantity * oi.unit_price)) OVER (), 1) AS percent
FROM order_items AS oi
JOIN books AS b ON b.id = oi.book_id
GROUP BY b.genre
ORDER BY position;
```

`SUM(SUM(…)) OVER ()` reads from the inside out: the inner `SUM` is each genre's revenue, and
the window adds those up across all genres.

That's the end of the SQL course. Try the quiz and the challenges, then go and ask your own
questions of the bookshop.
````
