**Goal:** Add SQL lessons 2 (*Finding the rows you want*), 3 (*Summarising data*) and 4 (*Combining tables*) on a new `bookshop` dataset.

**Architecture:** Content only. A new dataset file `app/database/datasets/bookshop.sql`. No API, web or mobile code changes.

**Tech Stack:** Laravel 13 / PHP 8.4, SQLite (3.53 via PHP's PDO in the sandbox), PHPUnit feature tests (`php artisan test`).

**Spec:** `docs/superpowers/specs/2026-10-08-sql-lessons-2-4-design.md`

## Global Constraints

- Lesson 1 does not change: its content, dataset (`bookstore`), quiz answers and challenge IDs stay as they are.
- Lessons 2–4 use the `bookshop` dataset; its `books` table has the same schema and rows as `bookstore`.
- Each new lesson: about 8 `## ` sections, 8 quiz questions with 4 options each, 6 challenges.
- Slugs: `finding-the-rows-you-want`, `summarising-data`, `combining-tables`, at positions 2, 3, 4.
- Each lesson only uses ideas it introduces or that earlier lessons taught. SQLite dialect.
- `order_matters` is true exactly when the prompt asks for an order; such prompts name a tie-breaker wherever the data has ties.
- Every ` ```sql ` block in the theory runs without error on the lesson's dataset, except blocks whose first line starts with `-- Error:`, which must fail.
- Every number quoted in a lesson or quiz was checked against the real data (they were, while writing this plan; the tests below keep them honest).

## Review Focus

1. **Re-seeding must not change lesson 1's IDs.** Learners' saved progress is keyed by quiz and challenge IDs; re-running the seeder must keep them. Test in Task 2.
2. **Lesson 1 must be untouched.** It must keep the `bookstore` dataset, and `bookshop.books` must equal `bookstore.books` row for row, so lesson 1's quiz answers hold if a learner compares. Tests in Tasks 1 and 2.
3. **"This fails" examples must actually fail.** A theory example that claims an error must produce one, or the lesson teaches something false. Test in Task 2 (applies to every later lesson).
4. **Quiz answers must point at a real option.** `correct_option` outside 0–3 would mark every learner wrong. Test in Task 2 (applies to every later lesson).
5. **The LEFT JOIN + COUNT(\*) mistake must be caught.** In *Orders per customer*, `COUNT(*)` gives customers with no orders a count of 1; the checker must reject it. Test in Task 4.

```php
    /**
     * @return list<list<mixed>>
     */
    private function rows(string $sql, string $dataset = 'bookshop'): array
    {

        $this->assertNull($run['error'], $run['error']['message'] ?? '');

        return $this->rows($sql)[0][0];

        $this->assertSame(
```

````markdown
## Matching patterns with LIKE

`=` only finds exact matches. To find text that *looks like* something, use `LIKE` with a
**pattern**. Two characters have a special meaning in a pattern:

| Symbol | Matches |
|--------|---------|
| `%` | any number of characters, including none |
| `_` | exactly one character |

```sql
SELECT title
FROM books
WHERE title LIKE 'The%';
```

`'The%'` means "starts with *The*". Move the `%` around to change the question:

| Pattern | Finds titles that… |
|---------|--------------------|
| `'The%'` | start with *The* |
| `'%Ring'` | end with *Ring* |
| `'%of%'` | contain *of* anywhere |
| `'_une'` | have exactly four characters and end in *une* |

```sql
SELECT title
FROM books
WHERE title LIKE '_une';
```

## Letter case and quotes

In SQLite, `LIKE` ignores the difference between upper and lower case for plain English
letters, so `'%the%'` finds *The Hobbit* as well as *The Name of the Wind*:

```sql
SELECT title
FROM books
WHERE title LIKE '%the%';
```

That returns 6 titles. `=` does care about case: `WHERE title = 'dune'` finds nothing,
because the title is stored as *Dune*. Other databases differ here; PostgreSQL's `LIKE`, for
example, is case-sensitive.

Text goes in single quotes, so what if the text itself contains one? Write it twice. One
customer is called *Siobhan O'Brien*:

```sql
SELECT name, email
FROM customers
WHERE name = 'Siobhan O''Brien';
```

## Checking against a list with IN

When a column can match any of several values, a chain of `OR`s gets long. `IN` takes a
list instead:

```sql
SELECT title, genre
FROM books
WHERE genre IN ('Horror', 'Romance');
```

That means exactly the same as `genre = 'Horror' OR genre = 'Romance'`. `NOT IN` keeps the
rows that match none of the values:

```sql
SELECT title, genre
FROM books
WHERE genre NOT IN ('Fantasy', 'Science Fiction');
```

## Ranges with BETWEEN

`BETWEEN low AND high` keeps values in a range. **Both ends are included**, so this is the
same as `price >= 10 AND price <= 15`:

```sql
SELECT title, price
FROM books
WHERE price BETWEEN 10 AND 15;
```

It works on dates too. The dates in this database are text in the form `YYYY-MM-DD`, which
sorts in date order, so you can compare them directly. These are the orders placed in
February 2026:

```sql
SELECT id, ordered_on
FROM orders
WHERE ordered_on BETWEEN '2026-02-01' AND '2026-02-28';
```

## Missing values: NULL

Two customers didn't give a city, and some orders haven't shipped yet. Those cells hold
`NULL`, which means "no value" or "unknown". It is not zero, and it is not empty text.

```sql
SELECT name, city
FROM customers;
```

Because `NULL` is unknown, comparing anything with it gives *unknown* too, never *true*. So
this finds **no rows**, even though two cities are missing:

```sql
SELECT name
FROM customers
WHERE city = NULL;
```

To test for a missing value, use `IS NULL`, or `IS NOT NULL` for the opposite:

```sql
SELECT name
FROM customers
WHERE city IS NULL;
```

```sql
SELECT id, ordered_on, shipped_on
FROM orders
WHERE shipped_on IS NOT NULL;
```

The same goes for `<>` and `NOT IN`: a comparison with `NULL` is never true, so a `NULL`
inside a `NOT IN` list makes the whole condition unknown for every row.

## Showing a fallback with COALESCE

`COALESCE` returns the first of its arguments that isn't `NULL`. Use it to show something
friendlier than an empty cell:

```sql
SELECT id, ordered_on, COALESCE(shipped_on, 'not shipped yet') AS shipped
FROM orders;
```

It only changes what the query shows. The data in the table stays `NULL`.

## Putting it together

These conditions combine with `AND`, `OR` and parentheses like any others. Customers in
London or Leeds whose name contains an *a* and who joined between December 2025 and March
2026:

```sql
SELECT name, city, joined_on
FROM customers
WHERE city IN ('London', 'Leeds')
  AND name LIKE '%a%'
  AND joined_on BETWEEN '2025-12-01' AND '2026-03-31'
ORDER BY joined_on;
```
````

````markdown
## Counting rows with COUNT

So far every query has returned rows from a table. **Aggregate functions** do something
different: they take many rows and boil them down to one value. The simplest counts rows:

```sql
SELECT COUNT(*) AS books
FROM books;
```

The result is a single row with a single number. `WHERE` still works, and it runs *before*
the counting, so only the rows it keeps are counted:

```sql
SELECT COUNT(*) AS fantasy_books
FROM books
WHERE genre = 'Fantasy';
```

## COUNT(column) skips NULLs

`COUNT(*)` counts rows. `COUNT(column)` counts the rows where that column **isn't** `NULL`:

```sql
SELECT COUNT(*) AS customers, COUNT(city) AS with_a_city
FROM customers;
```

That gives 10 and 8: two customers have no city. The same trick counts the orders that have
shipped:

```sql
SELECT COUNT(shipped_on) AS shipped
FROM orders;
```

## SUM, AVG, MIN and MAX

Four more aggregate functions do what their names say:

```sql
SELECT MIN(price), MAX(price), AVG(price), SUM(pages)
FROM books;
```

Averages often come out with long decimals. `ROUND(value, places)` tidies them up:

```sql
SELECT ROUND(AVG(price), 2) AS average_price
FROM books;
```

You can aggregate a calculation, too. Each line in `order_items` is worth
`quantity * unit_price`, so the shop's total takings are:

```sql
SELECT ROUND(SUM(quantity * unit_price), 2) AS revenue
FROM order_items;
```

Like `COUNT(column)`, these functions ignore `NULL`s.

## Counting different values with COUNT(DISTINCT …)

`COUNT(DISTINCT column)` counts how many *different* values a column holds:

```sql
SELECT COUNT(customer_id) AS orders, COUNT(DISTINCT customer_id) AS customers
FROM orders;
```

There are 20 orders, placed by 8 different customers.

## Groups with GROUP BY

One number for the whole table is useful, but usually you want one number *per something*:
books per genre, orders per customer. `GROUP BY` splits the rows into groups that share a
value, and the aggregate runs once for each group:

```sql
SELECT genre, COUNT(*) AS books
FROM books
GROUP BY genre;
```

You get one row per genre. Any aggregate works per group:

```sql
SELECT order_id, SUM(quantity) AS copies
FROM order_items
GROUP BY order_id;
```

## Grouped or aggregated: the one rule

After `GROUP BY`, each result row stands for a whole group. So every column you select must
either be one you grouped by, or be inside an aggregate function. What should this show in
the `title` column, when the Fantasy group holds six titles?

```sql
SELECT genre, title, COUNT(*)
FROM books
GROUP BY genre;
```

SQLite runs it anyway and quietly picks one title from each group, which is almost never
what you meant. Most other databases, such as PostgreSQL, refuse to run it. Stick to the
rule and you'll never be surprised.

## Filtering groups with HAVING

`WHERE` filters rows **before** they are grouped, so it can't see group totals:

```sql
-- Error: WHERE runs before the groups (and their counts) exist.
SELECT genre, COUNT(*)
FROM books
WHERE COUNT(*) > 3
GROUP BY genre;
```

To filter **groups**, use `HAVING`, which comes after `GROUP BY`:

```sql
SELECT genre, COUNT(*) AS books
FROM books
GROUP BY genre
HAVING COUNT(*) > 3;
```

You can use both. `WHERE` picks which rows go into the groups; `HAVING` picks which groups
come out. Genres with at least three books in stock:

```sql
SELECT genre, COUNT(*) AS in_stock
FROM books
WHERE in_stock = 1
GROUP BY genre
HAVING COUNT(*) >= 3;
```

## Sorting by an aggregate, and putting it together

`ORDER BY` can sort by an aggregate, or by its alias. Which customers order most often?

```sql
SELECT customer_id, COUNT(*) AS orders
FROM orders
GROUP BY customer_id
ORDER BY orders DESC;
```

The full order of the clauses is:

```sql
SELECT genre, ROUND(AVG(price), 2) AS average_price
FROM books
WHERE published_year >= 1900
GROUP BY genre
HAVING COUNT(*) >= 2
ORDER BY average_price DESC
LIMIT 3;
```

The database runs them in this order:

1. `FROM` picks the table.
2. `WHERE` keeps the matching rows.
3. `GROUP BY` splits them into groups.
4. `HAVING` keeps the matching groups.
5. `SELECT` calculates the columns, including the aggregates.
6. `ORDER BY` sorts the result.
7. `LIMIT` cuts it down to size.
````

Create `app/database/content/sql/04-combining-tables.md`:

````markdown
## Why data is split across tables

An order belongs to a customer. The shop could copy the customer's name and email into every
order, but then a customer who changes their email would have to be updated in many places,
and one missed row would make the data disagree with itself. Instead, each customer is
stored **once**, and an order just points at them:

```sql
SELECT id, customer_id, ordered_on
FROM orders
LIMIT 5;
```

- `customers.id` is the customers table's **primary key**: a value that identifies exactly
  one row.
- `orders.customer_id` is a **foreign key**: it holds the primary key of the customer who
  placed the order.

In the same way, `order_items.order_id` points at `orders.id`, and `order_items.book_id`
points at `books.id`. To answer questions like "who ordered what?", you follow these links
with a **join**.

## Joining two tables with JOIN … ON

`JOIN` puts two tables side by side. `ON` says which rows belong together:

```sql
SELECT orders.id, orders.ordered_on, customers.name
FROM orders
JOIN customers ON customers.id = orders.customer_id;
```

For each order, the database finds the customer whose `id` equals the order's
`customer_id`, and joins the two rows into one. Columns are written `table.column`, so it's
clear which table each one comes from.

`JOIN` is short for `INNER JOIN`: it keeps only the pairs that match. A customer with no
orders has nothing to pair with, so they don't appear.

## Table aliases, and ambiguous columns

Both tables have an `id` column, so a bare `id` doesn't say which one you mean:

```sql
-- Error: ambiguous column name, because orders and customers both have an id.
SELECT id, name
FROM orders
JOIN customers ON customers.id = orders.customer_id;
```

Writing the table name in front of every column fixes it, but gets long. Give each table a
short **alias** with `AS` instead:

```sql
SELECT o.id, o.ordered_on, c.name
FROM orders AS o
JOIN customers AS c ON c.id = o.customer_id;
```

Inside this query, `o` means `orders` and `c` means `customers`.

Don't forget the `ON`. Without it, SQLite pairs **every** customer with **every** order:
10 customers × 20 orders gives 200 rows of nonsense.

## Joining more tables

Each extra `JOIN` follows one more link. Every order with the books in it:

```sql
SELECT o.id AS order_id, b.title, oi.quantity
FROM orders AS o
JOIN order_items AS oi ON oi.order_id = o.id
JOIN books AS b ON b.id = oi.book_id
ORDER BY o.id;
```

Joined rows can be filtered and sorted like any others. Everything Amara Okafor has bought,
which takes all four tables:

```sql
SELECT c.name, o.ordered_on, b.title
FROM customers AS c
JOIN orders AS o ON o.customer_id = c.id
JOIN order_items AS oi ON oi.order_id = o.id
JOIN books AS b ON b.id = oi.book_id
WHERE c.name = 'Amara Okafor'
ORDER BY o.ordered_on;
```

## LEFT JOIN keeps rows with no match

An inner join drops customers who have never ordered. A `LEFT JOIN` keeps **every** row
from the table on its left; where there is no match on the right, the right-hand columns
are `NULL`:

```sql
SELECT c.name, o.id AS order_id
FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.id
ORDER BY c.name;
```

That returns 22 rows: the 20 orders, plus one row each for Isla Murray and Jonas Weber,
whose `order_id` is `NULL`. The order of the tables matters: the table you want to keep
whole goes on the left.

## Finding rows with no match

Those `NULL`s are useful. Keep only them, and you have the rows with no match at all, here
the customers who have never ordered:

```sql
SELECT c.name
FROM customers AS c
LEFT JOIN orders AS o ON o.customer_id = c.id
WHERE o.id IS NULL;
```

Test a column that can't be `NULL` in a real match, such as the right-hand table's `id`.
Then `NULL` can only mean "no match".

## Joins and GROUP BY

Joins and grouping work together: join first, then group the joined rows. How many books
has each customer bought?

```sql
SELECT c.name, SUM(oi.quantity) AS books_bought
FROM customers AS c
JOIN orders AS o ON o.customer_id = c.id
JOIN order_items AS oi ON oi.order_id = o.id
GROUP BY c.id, c.name
ORDER BY books_bought DESC;
```

Group by the customer's `id` as well as their `name`, so two customers who happen to share
a name stay separate.

To count matches *including zero*, combine a `LEFT JOIN` with `COUNT(column)`. `COUNT(*)`
would count the `NULL` row a customer with no orders gets, and report 1.

## Putting it together

Money is worked out from `order_items.unit_price`, the price the customer actually paid.
`books.price` is today's price, and two order lines were sold in a sale. Revenue per genre,
best first:

```sql
SELECT b.genre, ROUND(SUM(oi.quantity * oi.unit_price), 2) AS revenue
FROM order_items AS oi
JOIN books AS b ON b.id = oi.book_id
GROUP BY b.genre
ORDER BY revenue DESC;
```
````
