> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a follow-up check query to SQL challenges, then SQL lessons 5 (*Queries inside queries*), 6 (*Changing data*) and 7 (*Designing tables*).

**Architecture:** Challenges get an optional, hidden `check_sql`. When it is set, `SqlSandbox::check()` appends it to both the learner's SQL and the solution and compares the check's results, so lessons 6 and 7 can check what the learner's SQL *did*. The lessons follow the pattern of lessons 2–4: a Markdown file plus a PHP definition file in `app/database/content/sql/`, listed in `SqlCourseSeeder::BOOKSHOP_LESSONS`. No web or mobile changes.

**Tech Stack:** Laravel 13 / PHP 8.4, SQLite 3.53 (via PHP's PDO in the sandbox), PHPUnit feature tests (`php artisan test`, which prints JSON in this environment).

**Spec:** `docs/superpowers/specs/2026-10-08-sql-lessons-5-7-design.md`

## Global Constraints

- Slugs and positions: `queries-inside-queries` (5), `changing-data` (6), `designing-tables` (7), all on the `bookshop` dataset.
- Each lesson: about 8 `## ` sections, 8 quiz questions with 4 options each, 6 challenges.

- Every ` ```sql ` block runs without error, except blocks whose first line starts with `-- Error:`, which must fail.
- No challenge's solution appears in its lesson's quiz (enforced by an existing test).
- Every number quoted in the lessons was checked against the real data through the app's own `SqlSandbox` while writing this plan.

## Review Focus

1. **Existing challenges must behave exactly as before.** A challenge without `check_sql` must compare the learner's own last result, with today's messages. Test in Task 1 (plus the existing solution test).
2. **A follow-up that fails must not blame the learner's SQL.** If the learner forgot to add a column, the check query fails; the message must say the check failed and point at the missing change, not "Your SQL has an error". Test in Task 1.
3. **A learner's trailing comment must not swallow the check.** `UPDATE …; -- done` with no newline at the end must still be checked. Test in Task 1.
4. **An answer that changes nothing must never pass.** For every challenge with `check_sql`, the check on untouched data must differ from the solution's. Test in Task 3 (and it covers Task 4's challenges too).
5. **`check_sql` must not leak to the app.** It would hand learners the test. Test in Task 1.

Known limit, accepted: the sandbox runs at most 25 statements; a check adds up to 6, so a learner has at least 19 for their own SQL.

In `app/app/Sandbox/SqlSandbox.php`, replace the start of `check()`, from its docblock down to `if ($run['error'] !== null) { … }`, with:

```php
    /**
     * Runs the learner's SQL and the reference solution, then compares the last
     * result set each of them produced. With a check query, the check runs after
     * each of them and its results are compared instead, so a challenge can test
     * what the SQL changed.
     *
     * @return array{passed: bool, message: string, run: array, expected: ?array}
     */
    public function check(string $dataset, string $sql, string $solutionSql, bool $orderMatters, ?string $checkSql = null): array
    {
        // The newline ends a trailing "--" comment in the learner's SQL before the check starts.
        $withCheck = fn (string $script) => $checkSql === null ? $script : $script."\n;\n".$checkSql;

        $run = $this->run($dataset, $withCheck($sql));
        $expected = $this->lastRowSet($this->run($dataset, $withCheck($solutionSql))['results']);

        if ($expected === null) {
            throw new RuntimeException('Challenge solution does not return rows.');
        }

        $fail = fn (string $message) => ['passed' => false, 'message' => $message, 'run' => $run, 'expected' => $expected];

        if ($run['error'] !== null) {
            $failedInCheck = $checkSql !== null
                && $run['error']['statement'] !== null
                && $run['error']['statement'] >= count(StatementSplitter::split($sql));

            return $fail($failedInCheck
                ? 'Your SQL ran, but checking what it changed failed: '.$run['error']['message'].'. Make sure you made every change the challenge asks for.'
                : 'Your SQL has an error. Fix it and check again.');
        }
```

(`StatementSplitter` is in the same namespace, `App\Sandbox`, so no import is needed.) The rest of `check()` stays as it is.

````markdown
## A query inside a query

Which books cost more than the average? You could ask in two steps: run
`SELECT AVG(price) FROM books`, note the answer, then type it into a second query. Or let SQL
do both at once by putting the first query, in parentheses, inside the second:

```sql
SELECT title, price
FROM books
WHERE price > (SELECT AVG(price) FROM books)
ORDER BY price;
```

The inner query is a **subquery**. It runs first and produces one value, 14.62…, and the
outer query compares every price with it. You get 7 books.

A subquery used with `=`, `<` or `>` like this must return exactly **one value**. If it
returns several rows, SQLite quietly uses the first one, which is almost never what you
meant; most other databases stop with an error.

## Subqueries that return a list: IN

A subquery that returns a column of values works with `IN`, just like a list you type
yourself. Read this one from the inside out: the orders placed in April, then the books in
those orders, then their titles.

```sql
SELECT title
FROM books
WHERE id IN (
    SELECT book_id
    FROM order_items
    WHERE order_id IN (SELECT id FROM orders WHERE ordered_on >= '2026-04-01')
);
```

Each book appears once, even when it was in several of those orders, because the outer query
just asks "is this book's `id` in the list?".

## NOT IN and NULL

`NOT IN` with a subquery has the same trap you met with lists in lesson 2: if the subquery
returns a `NULL`, the condition is never true, and you get no rows at all. Daniel Kim has no
city, so this returns nothing:

```sql
SELECT name, city
FROM customers
WHERE city NOT IN (SELECT city FROM customers WHERE name LIKE 'D%');
```

The bug only appears when the data happens to contain a `NULL`, which makes it easy to miss.
When the subquery's column can be `NULL`, use `NOT EXISTS` instead.

## EXISTS and NOT EXISTS

`EXISTS (subquery)` is true when the subquery returns **at least one row**. What the rows
contain doesn't matter, so it's usual to write `SELECT 1`. Customers who have never placed an
order:

```sql
SELECT name
FROM customers AS c
WHERE NOT EXISTS (
    SELECT 1
    FROM orders AS o
    WHERE o.customer_id = c.id
);
```

And books that someone bought more than one copy of in a single order:

```sql
SELECT title
FROM books AS b
WHERE EXISTS (
    SELECT 1
    FROM order_items AS oi
    WHERE oi.book_id = b.id AND oi.quantity > 1
);
```

`EXISTS` only asks "is there a row?", so `NULL`s can't trip it up.

## Correlated subqueries

Look at the last two subqueries again: they use `c.id` and `b.id`, columns of the **outer**
query. A subquery like that is **correlated**: it is worked out again for each row of the
outer query.

That lets you compare each row with its own group. Books that cost more than the average
**for their genre**:

```sql
SELECT title, genre, price
FROM books AS b
WHERE price > (
    SELECT AVG(price)
    FROM books AS g
    WHERE g.genre = b.genre
);
```

The same table appears twice, so the aliases `b` and `g` are what tell the two apart.

## Subqueries in SELECT

A subquery that returns one value can also be a column. Each customer with the number of
orders they've placed:

```sql
SELECT name,
       (SELECT COUNT(*) FROM orders AS o WHERE o.customer_id = c.id) AS orders
FROM customers AS c;
```

Customers with no orders get 0. That's the same answer as the `LEFT JOIN` with
`COUNT(o.id)` from the last lesson, reached a different way.

## Subqueries in FROM

The result of a query is a table, so you can query it. What is an average order worth? You
need each order's total first, and then the average of those totals:

```sql
SELECT ROUND(AVG(total), 2) AS average_order
FROM (
    SELECT order_id, SUM(quantity * unit_price) AS total
    FROM order_items
    GROUP BY order_id
) AS order_totals;
```

An average order is worth 29.66. You can't do it in one step, because aggregates can't be put
inside each other:

```sql
-- Error: aggregate functions can't be nested.
SELECT AVG(SUM(quantity * unit_price))
FROM order_items
GROUP BY order_id;
```

## Join or subquery?

Many questions can be answered either way. As a rule of thumb, use a **join** when you need
columns from both tables in the result, and a **subquery** when the other table only decides
which rows to keep, or supplies a single value.

Who has bought *Dune* (book 6)? With a join, a customer who bought it twice appears twice,
so you need `DISTINCT`:

```sql
SELECT DISTINCT c.name
FROM customers AS c
JOIN orders AS o ON o.customer_id = c.id
JOIN order_items AS oi ON oi.order_id = o.id
WHERE oi.book_id = 6;
```

With a subquery, each customer is checked once, so duplicates can't happen:

```sql
SELECT name
FROM customers
WHERE id IN (
    SELECT o.customer_id
    FROM orders AS o
    JOIN order_items AS oi ON oi.order_id = o.id
    WHERE oi.book_id = 6
);
```

Next, try the quiz to check your understanding, then solve the challenges.
````

````markdown
## Changing data, safely

So far you've only read data. This lesson changes it: adding rows with `INSERT`, changing
them with `UPDATE` and removing them with `DELETE`.

In a real database these changes are permanent, so be careful. Here you can't break
anything: **every run starts from a fresh copy of the bookshop**, so a change lasts only
until the end of that run. That's also why each example below ends with a `SELECT`, to show
you the change before it disappears.

## Adding rows with INSERT

`INSERT INTO` names the table and the columns you're filling in; `VALUES` gives the values,
in the same order:

```sql
INSERT INTO customers (name, email, city, joined_on)
VALUES ('Lena Fischer', 'lena@example.com', 'Bristol', '2026-04-08');

SELECT * FROM customers WHERE name = 'Lena Fischer';
```

The `id` was left out, and the database filled it in with the next number, 11. Any other
column you leave out gets its default, or `NULL` if it has none. (The next lesson shows how
tables say what their defaults are.)

To add several rows at once, separate them with commas:

```sql
INSERT INTO customers (name, email, joined_on)
VALUES ('Omar Said', 'omar@example.com', '2026-04-08'),
       ('Priya Shah', 'priya@example.com', '2026-04-09');

SELECT id, name, city FROM customers WHERE id > 10;
```

## Copying rows with INSERT … SELECT

Instead of `VALUES`, an `INSERT` can take the rows a query returns. To put a free copy of
*The Remains of the Day* (book 12) into every order that hasn't shipped yet:

```sql
INSERT INTO order_items (order_id, book_id, quantity, unit_price)
SELECT id, 12, 1, 0
FROM orders
WHERE shipped_on IS NULL;

SELECT order_id, book_id, quantity, unit_price FROM order_items WHERE book_id = 12;
```

The query's columns fill the listed columns in order: each unshipped order's `id`, then the
fixed values 12, 1 and 0.

## Changing rows with UPDATE

`UPDATE` changes values in rows that already exist. `SET` says what to change and `WHERE`
says which rows:

```sql
UPDATE customers
SET city = 'Leeds'
WHERE id = 4;

SELECT id, name, city FROM customers WHERE id = 4;
```

To change several columns, separate them with commas: `SET city = 'Leeds', email = '…'`.

**Without a `WHERE`, `UPDATE` changes every row.** This sets every book's price to 5:

```sql
UPDATE books
SET price = 5;

SELECT title, price FROM books;
```

## Calculations and subqueries in UPDATE

The new value can be calculated from the old one. Classics published before 1900 go up by 1:

```sql
UPDATE books
SET price = price + 1
WHERE published_year < 1900;

SELECT title, published_year, price FROM books WHERE published_year < 1900;
```

`WHERE` can use a subquery, too. Take every book that has never sold out of stock:

```sql
UPDATE books
SET in_stock = 0
WHERE id NOT IN (SELECT book_id FROM order_items);

SELECT title, in_stock FROM books;
```

(`NOT IN` is safe here: `book_id` can never be `NULL`.)

## Removing rows with DELETE

`DELETE FROM` removes the rows `WHERE` matches. To take *A Wizard of Earthsea* out of order 20:

```sql
DELETE FROM order_items
WHERE order_id = 20 AND book_id = 8;

SELECT * FROM order_items WHERE order_id = 20;
```

Foreign keys protect the links between tables. Amara Okafor has orders that point at her, so
the database refuses to delete her:

```sql
-- Error: customer 1 still has orders, and the foreign key protects them.
DELETE FROM customers
WHERE id = 1;
```

A customer with no orders, such as Isla Murray, can be deleted. And like `UPDATE`, **`DELETE`
without `WHERE` removes every row** of the table.

## Look before you change

The safest habit with `UPDATE` and `DELETE`: write the `SELECT` first, with the `WHERE` you
plan to use, and check it returns exactly the rows you mean.

```sql
SELECT id, title, published_year
FROM books
WHERE published_year < 1850;
```

Two books. Now you can swap the first line for the change, keeping the `WHERE` as it is:

```sql
UPDATE books
SET in_stock = 0
WHERE published_year < 1850;

SELECT title, in_stock FROM books WHERE published_year < 1850;
```

## Transactions

Some changes belong together: cancelling an order means deleting its lines *and* the order.
A **transaction** groups statements so that they all happen, or none do.

- `BEGIN` starts a transaction.
- `COMMIT` keeps every change made since `BEGIN`.
- `ROLLBACK` undoes them all.

```sql
BEGIN;

UPDATE books SET price = 0;
SELECT title, price FROM books LIMIT 3;

ROLLBACK;

SELECT title, price FROM books LIMIT 3;
```

The first `SELECT` sees free books; after `ROLLBACK`, the prices are back. In a real database,
if something goes wrong in the middle of a transaction, rolling back leaves the data as it
was, instead of half changed.

Next, try the quiz to check your understanding, then solve the challenges. They check the
data after your SQL has run, so you don't need to finish with a `SELECT`.
````

````markdown
## Creating a table

Every table you've used so far was created with `CREATE TABLE`. You name the table, then
list its columns, each with a **type**:

```sql
CREATE TABLE publishers (
    id      INTEGER PRIMARY KEY,
    name    TEXT NOT NULL,
    founded INTEGER
);

INSERT INTO publishers (name, founded) VALUES ('Bloomsbury', 1986);
SELECT * FROM publishers;
```

SQLite's main types are `INTEGER` (whole numbers), `REAL` (decimals), `TEXT` and `BLOB` (raw
bytes). It has no separate date type, which is why the bookshop stores dates as text in the
form `YYYY-MM-DD`.

SQLite is relaxed about types: a column's type is a preference, not a rule. It will happily
store text in an `INTEGER` column:

```sql
CREATE TABLE notes (pages INTEGER);
INSERT INTO notes VALUES ('lots');
SELECT pages, typeof(pages) FROM notes;
```

Most other databases would refuse. In SQLite you can ask for that strictness by adding
`STRICT` after the closing parenthesis of `CREATE TABLE`.

## Primary keys

A **primary key** identifies each row, so no two rows may share one. A column declared
`INTEGER PRIMARY KEY` is special in SQLite: leave it out when you insert, and the database
numbers the rows for you, as you saw with `customers` in the last lesson.

```sql
-- Error: two shelves can't share the same code.
CREATE TABLE shelves (code TEXT PRIMARY KEY, room TEXT);
INSERT INTO shelves VALUES ('A1', 'Front');
INSERT INTO shelves VALUES ('A1', 'Back');
```

A primary key can span several columns. `order_items` uses the pair
`(order_id, book_id)`: an order can't list the same book twice, but different orders can
contain the same book. `PRAGMA table_info` shows a table's columns, and the `pk` column
numbers the primary key's parts:

```sql
PRAGMA table_info(order_items);
```

## NOT NULL and DEFAULT

`NOT NULL` makes a column required. `DEFAULT` gives the value to use when an `INSERT` leaves
the column out:

```sql
CREATE TABLE events (
    title     TEXT NOT NULL,
    starts_on TEXT NOT NULL,
    room      TEXT NOT NULL DEFAULT 'Main shop'
);

INSERT INTO events (title, starts_on) VALUES ('Poetry night', '2026-05-01');
SELECT * FROM events;
```

Leaving out a required column with no default is an error:

```sql
-- Error: starts_on is required.
CREATE TABLE events (title TEXT NOT NULL, starts_on TEXT NOT NULL);
INSERT INTO events (title) VALUES ('Book swap');
```

A default is only used when the column is left out. Writing `NULL` yourself stores `NULL`, or
breaks `NOT NULL`.

## UNIQUE

`UNIQUE` stops two rows having the same value in a column:

```sql
-- Error: the gift card code GIFT-10 is already taken.
CREATE TABLE gift_cards (code TEXT NOT NULL UNIQUE, amount REAL NOT NULL);
INSERT INTO gift_cards VALUES ('GIFT-10', 10);
INSERT INTO gift_cards VALUES ('GIFT-10', 25);
```

One surprise: `NULL` doesn't count as a value here, so a `UNIQUE` column can hold any number
of `NULL`s. Add `NOT NULL` if every row must have a value. `UNIQUE (a, b)` written after the
columns makes a *combination* of columns unique.

## CHECK

`CHECK` adds your own rule. Each row must make the condition true:

```sql
-- Error: a stock count can't be negative.
CREATE TABLE stock_counts (
    book_id INTEGER NOT NULL,
    copies  INTEGER NOT NULL CHECK (copies >= 0)
);
INSERT INTO stock_counts VALUES (1, -2);
```

Any condition you could write in a `WHERE` works, such as `CHECK (price > 0)` or
`CHECK (genre IN ('Fantasy', 'Horror'))`.

## Foreign keys

A **foreign key** says that a column holds another table's primary key, with
`REFERENCES table (column)`. The database then refuses values that point at nothing:

```sql
CREATE TABLE loans (
    id          INTEGER PRIMARY KEY,
    customer_id INTEGER NOT NULL REFERENCES customers (id),
    book_id     INTEGER NOT NULL REFERENCES books (id)
);

INSERT INTO loans (customer_id, book_id) VALUES (1, 6);
SELECT * FROM loans;
```

```sql
-- Error: there is no book 99.
CREATE TABLE loans (
    id          INTEGER PRIMARY KEY,
    customer_id INTEGER NOT NULL REFERENCES customers (id),
    book_id     INTEGER NOT NULL REFERENCES books (id)
);
INSERT INTO loans (customer_id, book_id) VALUES (1, 99);
```

It also works the other way: as you saw in the last lesson, you can't delete a customer while
their orders still point at them.

SQLite only enforces foreign keys when they are switched on with the setting
`PRAGMA foreign_keys = ON`. This sandbox switches it on for you; in your own SQLite
databases, run that setting each time you connect.

## Changing and removing tables

`ALTER TABLE` changes a table that already exists. The most common change adds a column; the
existing rows get `NULL` (or the column's default):

```sql
ALTER TABLE books ADD COLUMN isbn TEXT;
SELECT title, isbn FROM books LIMIT 3;
```

`ALTER TABLE … RENAME COLUMN old TO new` renames a column, and `ALTER TABLE … RENAME TO new`
renames the table.

`DROP TABLE` removes a table and everything in it. Unlike `DELETE FROM`, which empties a table
but keeps it, there is nothing left afterwards:

```sql
DROP TABLE order_items;
SELECT name FROM pragma_table_list WHERE schema = 'main' AND name NOT LIKE 'sqlite_%';
```

## Putting it together

A table for book reviews: each review belongs to a book and a customer, has between 1 and 5
stars, gets today's date unless told otherwise, and each customer can review a book only once.

```sql
CREATE TABLE book_reviews (
    id          INTEGER PRIMARY KEY,
    book_id     INTEGER NOT NULL REFERENCES books (id),
    customer_id INTEGER NOT NULL REFERENCES customers (id),
    stars       INTEGER NOT NULL CHECK (stars BETWEEN 1 AND 5),
    written_on  TEXT    NOT NULL DEFAULT '2026-04-08',
    body        TEXT,
    UNIQUE (customer_id, book_id)
);

INSERT INTO book_reviews (book_id, customer_id, stars, body)
VALUES (6, 2, 5, 'Worth every page.');

SELECT b.title, c.name, r.stars, r.written_on, r.body
FROM book_reviews AS r
JOIN books AS b ON b.id = r.book_id
JOIN customers AS c ON c.id = r.customer_id;
```

Every rule a table enforces is one mistake your data can never contain.
````
